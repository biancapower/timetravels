# 0004. Test-first for the time logic; every commit green

**Context.** `src/time/` is pure logic with hard cases (daylight-saving transitions, times that do not exist, times that happen twice). It is the part of the project where test-first pays off most, and the part whose history will be read most closely.

**Decision.** `src/time/` is developed test-first: write the test, run it and see it fail, then write the implementation. Red is a working-tree state, never a commit. Planned cases may be committed ahead of their code as `test.todo` stubs, a name with no body, so a pull request can carry the acceptance criteria in the suite from its first commit; a skipped test with a body is never committed. Each commit holds the test and the code that passes it, and the check command is green on every commit. The interface is test-alongside: build, check live, then write the Playwright test from the issue's acceptance criteria. Pull requests land on `main` with a merge commit, so the small commits survive.

**Alternatives.** Separate red and green commits inside each pull request, considered and rejected: a commit that fails its own tests breaks `git bisect`, fails the "would the codebase be coherent if this commit were reverted" test, and shows test-first as presentation rather than substance. Squash-merging, which would lose the small commits.

**Reasons.** Test-driven development is defined as the red-green-refactor cycle and says nothing about commits (Fowler, [Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html)). Git's own [SubmittingPatches](https://git-scm.com/docs/SubmittingPatches) asks that each commit be "a self-contained, buildable, testable unit", and Google's [small CLs guide](https://google.github.io/eng-practices/review/developer/small-cls.html) and Git's [bisect documentation](https://git-scm.com/docs/git-bisect) assume the same. The evidence that the test came first is the test's existence and the order of the work, not a red commit. Stubs are allowed because they recover what red commits were meant to show: the cases were named before the code, in the history, without any commit failing its own tests. `test.todo` is the runner's own form for this and reports as a count, so an unfinished stub is visible, not hidden. Skipped tests with bodies are forbidden for the opposite reason: a disabled test looks like coverage and is not, and nothing counts it.

**Consequences.** A pull request's commits can each be checked out and run. Nothing in CI needs to tolerate a failing commit. A `todo` in the suite is a promise with a visible count, not a hidden failure; the check command fails on `test.only` so nothing narrows the run by accident.

**Status.** Approved by @biancapower, 2026-10-09.
